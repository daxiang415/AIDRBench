# 工作负载构成与下游结果重算（2026-09-09）

## 纠正的研究问题

旧稿将训练和离线推理各设为总 GPU 小时的一半，并分别允许 100% 和 50% 延后，得到 75%。这是一组人为设置，不能由 Alibaba 数据来源或均衡抽样方法推导，也没有证据表明它代表实际混合业务数据中心。旧稿虽然扫描了较低的可延后比例，但独立容量认证、重复调用、可再生能源与经济结果仍主要来自 75% 配置，不能据此声称低比例下的下游结论已经检查完整。

本轮按作者要求，计算 5%、10%、20%、40%、60% 五档。不改原有 locked 输入、证书和计算结果；不填作者待定信息。旧的 75% 情景作为历史高灵活性基准保存，不再作为实际数据中心的代表性依据。

## 数据依据与分母

`source_audit.py` 流式核对完整的 40,522,321 行标准化执行记录，用原始未截尾时长乘以申请 GPU 数进行汇总。输入 SHA-256 与原数据清单一致。结果包括在线推理 54.495%、离线推理 21.519%、训练 19.423%；开发及其他/未知类别全部保留在分母。低优先级训练与低优先级离线推理合计 22.028%。

这个分母是申请资源的执行时长，既不是实际功耗，也不是有效算力、独立作业数量或可延后资格。原预处理为了作业形状抽样而截尾的时长不用于本次总体构成统计。源表一行是 pod/workload 的执行区段，并不等于一个独立用户作业；不能把 79.45% 的离线推理**记录数**误认为相同的资源时间比例。

[Alibaba 原论文](https://www.usenix.org/system/files/osdi26-li-suyi.pdf) 区分在线服务与批量推理，并描述训练和在线推理以高优先级为主。其研究对象是共享生产基础设施，排除了专用大模型超大规模预训练集群。因此这些数据约束本研究的情景设计，不能概括所有运营商。[官方字段说明](https://github.com/alibaba/clusterdata/blob/master/cluster-trace-gpu-v2026/docs/schema.md) 解释了执行区段、GPU 申请量和优先级字段。

## 五档比例的含义

| 档位 | 构成与资格规则 | 能否称为实测可延后比例 |
|---|---|---|
| 5%、10%、20% | 保留原始六类资源时间构成，对低优先级训练和离线推理采用共同的获准延后系数 | 不能。只有候选池构成来自数据；是否允许等待及期限仍是假设 |
| 40% | 保留原构成，先纳入低优先级批处理，再假定其余批处理中的一部分也获得资格，接近全部 40.94% 批处理 | 不能。需要高优先级批处理也获准调整，是对照情景 |
| 60% | 原构成不可能支持。显式将约 19.06 个百分点的在线业务改为离线批处理，再令全部训练与离线批处理有资格 | 不能。是业务结构改变的反事实，不能解释为同一生产混合负荷的简单敏感性 |

所有档位均不允许在线推理跨小时延后。40% 和 60% 不能据此宣称实际部署的灵活性达到这些水平。

## 计算设计与比较边界

- 总硬件 576 GPU、总工作量 374.4 GPU 小时/小时保持一致。灵活池 GPU 比例与可延后工作比例匹配，保持两池平均利用率约 65%，显式保留整数 GPU 取整。这样不需要用过度闲置或平均超载的池去承接极低/极高比例。这是固定的分配规则；跨档比较是这项分配政策下的结果，不能把所有变化都归因于资格一个因素。
- 同一种子先生成一份 60% 情景的可分割工作模板，其他档位只按类别缩放 GPU 小时，保留释放时刻、截止时间、社区曲线与事件锚点。主张配对的依据是这些显式检查，不能只靠“用了同一个种子”。
- 训练/离线推理工作形状沿用已有低优先级抽样库和声明的合成期限。40% 高优先级资格对照和 60% 业务转换不构成高优先级生产作业的实证重放。
- 训练/离线推理的功率系数取自既有板卡测量。在线及开发/其他刚性负荷的功率系数暂以离线推理系数作工程代理；明确不称为在线推理测量。刚性负荷在现有小时级模型中是固定用电，在线服务延迟并未被独立模拟。
- 新开发集 100 个种子，新确认集 300 个种子；规划与光伏使用每个集合预先固定的前 100 个种子。旧的 locked 集不被重开。预运行种子独立保存，不计入正式结果。
- 四小时和八小时是本轮完整贯通的服务时长。单次候选按开发规划下界的 50%、75%、90%、100% 搜索，用开发 Wilson 单侧 95% 下界选择，再在确认集检验 0、2、6 小时通知；确认结果不用于重新选容量。
- 重复调用选择与旧结果相对应的两个关键对照：四小时调用/八小时间隔、八小时调用/十二小时间隔，各四次。开发选择重复方案；确认时同时计算同请求的连续方案与四个相同时刻的独立单次反事实。两者都要求四次全部成功。
- 光伏承载及固定 500-kW 光伏利用量在有/无储能条件下重算，刚性/灵活调度配对，使用零截止时间损失约束。物理模块规模按固定 GPU 数计算，不强行归一回旧的 201 kW。所有五档采用共同的 1.1-MW 接入上限：原 1-MW 上限下，开发种子 930096 的三种配置在无响应时即超限，因此在正式规划和容量选择前调整共同上限，初始 2,000 份基准保留在 v1 目录。新上限高于 800-kW 背景峰值加上全部配置的最大类别功率峰值，并非随比例改变。
- 经济核算使用每种配置自己的容量与完整响应/无响应小时账本。单次采用每年 50 次独立调用；四调用序列采用每年 12 个独立序列。固定站点成本只记一次，年度抽样不是全年连续调度。保留未成功轨迹；若容量未通过确认，不能报为已经合格的盈利方案。

上述设计贯通五个档位的主要证据链，不代表所有参数同时变化的全局敏感性，也不把没有重算的旧时长/地域/连续运行结果自动转移到新场景。原始输入、选值表、逐事件和逐小时结果、光伏配对结果将单独导出供直接重绘。

## 完成的有效执行版本

主体与四个独立对照的全部计算已经完成，正式数值审核通过。保存了 3,200 份无响应基准、2,800 个 PI 最优值、34,400 次正式控制器运行、55,400 条事件结果、7,430,400 行小时数据和 7,200 个光伏/储能优化结果。全部光伏结果由原求解流程完成，未采用数值加速尝试替代结果；所有光伏期限损失为零。微小储能利用率差异的最优性精度限制仍须保留。

主体协议为 `protocol_final.json`，控制器为 `study_controller_v4.py`，有效结果在 `results/nature_mainline/workload_composition_v4/`。开发种子 930000–930099，确认种子 960000–960299。重复调用仅使用 `repeat_duration_protocol_v2.json` 与 `run_repeated_duration_v2.py`，有效目录为主体目录下的 `repeat_duration_corrected_v2/`。恢复保护的分母、float32 舍入和重复调用实际时长修正均有可检查记录；错误的一小时重复诊断被排除，旧证书及中间版本仍保留。

五档单次承诺分别为 2.95、5.90、11.80、22.19、34.00 kW，四小时均为 295/300 成功，八小时均为 292/300。提前 0、2、6 小时通知未改变本轮固定请求的配对成功结果。原承诺用于四小时/八小时间隔重复方案，五档均为 300/300 成功；用于八小时/十二小时间隔方案，成功数依次为 268、256、250、249、241，均未通过确认标准。另行开发网格没有选出重复候选，不能将其解释为重复容量为零，也不能抹去四小时原对照的成功结果。

审核检查全部正式事件的时长与成功标准、444 份代表账本的独立算术，以及全部小时数据核心列。28 套情景恢复后的原始文件哈希完全一致；一套恢复输入重新运行后，216 小时的 87 个数值列与原轨迹相符。详见各审核 JSON 与 `RESULTS_AND_REASONS_ZH.md`。
