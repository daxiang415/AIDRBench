# 实测与连续运行：建议补充方案

日期：2026-09-08。状态：**设计草案，尚未执行，也不是新增研究结果。** 本文回答如何补齐 v0.18 的关键证据缺口；不改动既有论文结果、冻结证书和绘图包，下面的时长和实验档位是建议起点，并非期刊规定或已完成的样本量论证。

后续范围澄清：直接对照作者指定的深圳 DR 参考文章后，本文件保留为**可选扩展方案**，不作为投稿前默认必须全部完成的清单。该参考文章采用每季一周的模型调度，也未建立完整市场盈利或个体电池退化分析。当前优先级与比较依据见[直接内容比较](/home/user/projects/AIDRBench/manuscript/reviews/dr_reference_comparison_2026-09-08.md)。

## 1. 现在已经有什么，还缺什么

已有四张 RTX PRO 6000 的功率测量：训练和离线推理各测 1 GPU、4 GPU，每条件三次；预热 5 s，正式测量 20 s。原始工作负载主要是矩阵运算，四卡训练包含梯度通信。对应脚本为 `scripts/run_minimal_gpu_power_calibration.sh`、`scripts/gpu_power_workload.py`，数据在 `data/calibration/rtx6000pro_4gpu_v1_raw/`。

这些测量支持局部板卡功率标定。它们没有测完整训练任务的检查点保存、暂停、重新加载、丢失进度、恢复吞吐或整机供电功率。现有记录也没有证明原服务器现在仍然可用。

连续调用已经完成独立开发和确认，每个方案包含四次调用。年化经济账本从完整四调用序列抽样，保留序列内部历史，但序列之间独立。它还不是作业队列贯穿全年的连续模拟。

两项补充应连接起来：**先测出控制操作的实际代价，再观察这些代价在连续作业与反复调用下是否积累到影响服务和收益。**

## 2. 实测：从一台服务器做完整的响应与恢复

### 2.1 设备和工作负载

优先复用原四卡节点，减少新硬件造成的解释变化。只有单卡也能做初步恢复测量，但多卡同步恢复需要四卡或另一台多卡节点单独验证。

增加至少一个包含真实优化器更新的训练任务和一个固定输入集的离线推理任务。模型、输入、批量大小、精度、目标训练步数或推理样本数全部记录并冻结。保留原矩阵工作负载作功率对照，不把它直接称作完整应用验证。

记录 GPU 板卡功率、利用率、温度、有效工作进度、队列和操作时间戳。有可用计量 PDU、电表或经过核对的 BMC 整机功率通道时，同时记录整机输入功率；没有时继续明确板卡与整机的证据边界。即使测到了单机输入功率，机房冷却和设施 PUE 仍需独立证据。

NVIDIA 文档区分板卡平均功率、瞬时功率与特定平台的模块功率；平均功率的时间窗不能通过更频繁轮询变成更高分辨率的物理测量。先确认传感器支持与实际更新时间，以约 1 s 记录作为能量核算起点，响应速度的结论服从真实采样能力。[NVIDIA nvidia-smi 文档](https://docs.nvidia.com/deploy/nvidia-smi/index.html)

### 2.2 对照条件

| 条件 | 具体操作 | 主要回答 |
| --- | --- | --- |
| 无响应基准 | 相同任务、输入和到达时序，按预定无响应调度完成 | 正常情况下的功率、吞吐、完成时间和质量 |
| 内存保留暂停 | 在安全的计算步边界暂停可延后任务，保留状态；事件结束后继续 | 不写盘时，暂停能降多少功率、恢复多快 |
| 检查点退出恢复 | 保存状态并退出，随后重新加载并继续 | 需要释放资源时的真实保存、加载、重做和能耗代价 |

先分别标定两种恢复方式，再冻结主实验采用的方式。多卡作业保持真实的卡数需求和同步关系，不把一个四卡作业当成四个可任意分割的单卡作业。第一阶段无需把功率封顶另立为主要干预，以免偏离论文的作业延后机制。

训练恢复至少保存模型和优化器状态；本项目还应保存迭代位置、数据读取位置、随机数状态和适用的混合精度状态，以检查是否重复或漏算工作。恢复后比较固定有效工作量下的损失、验证指标和输出完整性。PyTorch 官方教程说明了恢复训练时同时保存模型和优化器状态的基本做法。[PyTorch 检查点教程](https://docs.pytorch.org/tutorials/beginner/saving_loading_models.html)

### 2.3 从短实验到连续多次调用

1. **短实验标定**：先用 5、15、60 min 的暂停窗口观察功率下降和恢复行为。工作量应足够覆盖整个响应及恢复过程，不能在事件前自然结束。先试运行获取方差与耗时，再按目标误差精度冻结正式重复数。
2. **配对重复**：每对实验使用相同初始状态和任务输入，随机安排有响应与无响应的执行顺序；不同批次重新初始化，记录温度和共享资源干扰。相同运行中的四张卡和连续功率读数均为相关测量，不增加独立运行数。
3. **多次调用验证**：在持续接收新作业的 24–72 h 实验中插入多次响应，队列不因调用结束而重置。至少覆盖一个恢复充足方案和一个恢复紧张方案，追踪后来到达任务是否受到前次响应影响。
4. **时长覆盖**：短实验只标定开销，不能声称直接验证了论文的 4 h 或 8 h 服务。需要支持哪个实际服务时长，就增加相应的长时调用实验；否则明确长时结论仍来自测量约束下的模拟。

不要在同一组少量实验中调参数、选最优方案后再声称独立确认。用于拟合功率和恢复开销的运行与用于检查预测误差的运行分开；少数成功实验只能展示可行性，不能据此宣称已经获得 95% 可靠性认证。

### 2.4 必须留下的数据和结论

每次实验保留命令发出、真正停止有效计算、保存结束、重新启动、恢复稳定吞吐的时间戳，以及逐时刻功率和有效工作进度。不要仅记录脚本的启动与退出时间。

主要指标包括实际功率降幅、响应延迟、保存和加载耗时、进度损失、额外完成时间、恢复期功率峰值、完成同等有效工作量的总能耗，以及期限/质量是否满足。用任务剩余工作量核对计算守恒；所有失败及其原因保留。

将这些测量转换为分工作负载的吞吐、暂停恢复延迟、额外能耗和必要的重做工作量，加入新版本模拟；新旧模型对同一批新情景做配对比较。若仍采用小时步长，秒级操作应按有效算力损失和能量积分折算，不能简单将一分钟开销进位成一小时停机，也不能据此给出秒级响应认证。

## 3. 连续运行：让积压和恢复约束贯穿完整日历

### 3.1 改动重点

现有参考配置是 7 d 作业到达、48 h 清空尾段和 6 h 因果预测窗口；连续扩展见 `src/aidrbench/evaluation/repeat_capacity.py`。新增实现要同时改变输入生成、状态延续、评价边界和经济账本，不能只把 `episode_days` 改成 365。

- 连续输入作业，跨天、跨月保留队列、原始截止时间、任务进度及尚未结束的恢复义务；分批保存结果可以，分批重置物理状态不可以。
- 用滚动控制处理 30 d、90 d、365 d。365 d 是 8,760 个小时步；控制器仍只得到所声明的因果信息和预测窗口，不因此看到全年未来。
- 先评估预热期长度，避免用空队列启动制造额外灵活性。已有队列及其年龄、剩余工作量应一致地进入有响应和无响应分支。
- 年末保留正常作业到达并延长观察，跟踪计分年内到达任务的最终完成情况；延长期至少覆盖这些任务的截止时间和未结束的响应恢复义务。延长期成本和年末欠账单列。不能年末关掉到达、免费清空积压后说全年服务合格。
- 分别核查物理功率限额和合同恢复包络；冻结原控制器作为参考。若开发新的恢复约束或控制策略，应另行选择和独立确认，不覆盖旧结果。

最后两点很重要：本轮已经发现部分严重失败依赖到达停止后的恢复基准下降。连续实验必须消除这个人为终点，并检查恢复是否真正依靠可用资源，而不是记账边界。

### 3.2 情景与对照

先在参考运行点和已发现的恢复紧张条件开发、排查，再加入已通过基准服务检查的低可调工作比例与高负荷点。正式比较之前冻结选择标准，完整记录不可行条件，不为改善响应成功率而事后删掉难例。

建议初始调用档位为每年 12、48、96 次，每个固定时长内比较均匀分布、短期集中和负荷高峰相关调用。比较调用聚集效应时保持全年调用次数、单次时长和请求容量相同。没有实际市场调用记录时，这些是合成压力方案，并不是某市场真实规则。

每条长期情景至少比较：原已认证单次容量、连续研究选出的对应方案容量、同一控制器关闭响应后的运行。额外保留原全速无响应基准，检查经济差异有多少来自调度策略本身。新的“按状态拒绝接单”策略可以作为单独研究，但必须报告拒绝次数、可用率、实际履约和收入，不能靠拒接把固定承诺的可靠性做高。

有全年真实作业与社区时序时按原时间顺序使用，并保留日期覆盖信息；只有数周输入时，采用有明确来源标签的时序模型或成块重采样。报告相关性、季节假设、拼接边界和输入周复用情况。**短轨迹生成的全年情景是合成年模拟，不是全年实测。**

### 3.3 评价什么

| 层面 | 核心指标 | 避免的误判 |
| --- | --- | --- |
| 每次调用 | 实际交付、持续时间、恢复负担、发生前积压 | 只统计事件内降功率而漏掉恢复 |
| 作业服务 | 期限违约工作量、等待时间分布、质量、原计分作业最终状态 | 只看全年平均值掩盖某月严重违约 |
| 持续运行 | 相对无响应的积压走势、月度分布、长时间拥堵、跨年残余义务 | 把正常运行中的非零队列误当作失败，或把持续累积当作稳定 |
| 年度可靠性 | 调用成功比例、连续失败次数，以及另行定义的全年合同通过指标 | 混同“95% 调用成功”与“95% 年份全部成功” |
| 经济性 | 同一时间轴上的收入、电费、等待代价、丢失工作、恢复开销、合同扣款 | 重复收取固定成本、重复计入重叠小时或忽略失败成本 |

全年账本按小时只记录一次；固定年度费用只计一次；年末未完成义务及对应延后成本做期末调整，避免截断收益。GPU 购置和折旧需要实际价格、使用年限、残值、用途分摊和是否新增预留设备的记录。基准与响应两种运行共同承担的设备成本不应无理由全部归入需求响应；新增预留设备或可归因的增量成本单独计入。短实验不能直接测出长期老化费用。

统计单位是独立完整运行/情景，不能把同一年 8,760 个相关小时当作 8,760 个独立样本。调用层面的不确定性按完整年情景聚类；年度事件定义、确认样本数和误差目标在开发试运行后冻结，再使用独立确认输入。重复使用有限生产周并不会增加独立观测年份。

## 4. 推荐执行顺序和交付边界

1. **先完成软件与数据设计**：生成持续到达和调用日历，实现状态连续、期末义务追踪、配对无响应分支和统一账本。增加跨分块状态一致性、工作量守恒、成本不重复、未来信息不泄漏等必要测试。
2. **30 d 开发试跑**：测算运行成本，核查基准可行性、队列走势、期末延长规则及预热敏感性；这一步不发布全年可靠性结论。
3. **并行开展节点实测**：有可用 GPU 服务器即可做标定和短期多次调用。需要明确设备型号/卡数、计量通道、代表性任务以及允许使用的时间窗口；远程登录凭据不写进论文或公开记录。
4. **把实测参数接回模拟**：记录模型版本差异，冻结候选容量和确认方案，再做独立的 90 d/全年评价。先保留不含新测量开销的参考分支，以便解释容量变化来源。
5. **按结果修改文章**：正文集中回答实际恢复开销是否改变可兑现容量、长期积压是否稳定、连续年度账本是否仍支持参与。设备细节、完整测试矩阵和原始记录进补充材料及绘图数据。

如果没有 GPU 服务器，连续运行的软件和合成情景仍可先推进；硬件部分保持“待测”。如果只能测单机，文章应表述为单机恢复验证和测量约束下的系统模拟；只有获得机房侧计量与实际调度记录后，才可进一步支持设施尺度验证。

这一组合有助于补强论文的证据链，不保证某个期刊录用，也不要求先运营一个真实数据中心一年才能开展下一步工作。
